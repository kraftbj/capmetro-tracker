## Problem Statement

Two kids ride CapMetro to high school in Austin. Their trips involve transfers, not single
routes: one rides the **800 to the 4 Austin HS run** in the morning and **4 to 837** home;
the other (McCallum HS) varies, taking **337 to 350**, or on one recent day **337 to 7 to 837**.

The parent wants to know two things that today require squinting at a cluttered app: where
the buses on those routes actually are, and how late each one is running against its schedule
so a kid standing at a stop knows whether to keep waiting.

The Transit app has this data but presents too much of it to read at a glance. A prior
community site, realtimebustracker.com, did roughly the right thing but no longer displays data.

Direct quote that defines the target:

> "I'm not looking for clean answers but more of a **dispatch board** so I can quickly
> understand the CMTA picture."

## What Makes This Cool

Three things, in ascending order of "nobody else builds this":

1. **Schedule adherence per vehicle, stated in plain terms.** Not "arriving in 7 min" but
   "#2641 is the 9:33 trip, running +3, next stop Campbell/5th at 9:36 against a scheduled 9:33."
2. **Special trip pattern detection.** Route 4 runs 9 distinct stop patterns. Two of them have
   exactly 2 trips per day (08:15 and 16:15) and those are the ones that serve Austin High via
   Veterans/Atlanta while *skipping* Campbell/5th. No consumer transit app surfaces "this bus is
   running the special pattern, so your usual stop is not served today." This falls out of a
   GROUP BY on each trip's ordered stop-ID signature.
3. **Saved trip watches.** Pin "the 7:50a 800 SB from Simond/Berkman" and watch that specific
   trip from roughly an hour before until it clears the stop.
4. **Turnaround continuity via block IDs.** This is the sleeper feature. On route 4,
   Campbell/5th is the turnaround: a vehicle runs westbound, arrives, lays over, and departs
   eastbound as a *different trip ID with the same `block_id`*. Transit's eastbound view shows
   nothing, because the bus is not eastbound yet. A rider standing there sees an empty map and
   concludes no bus is coming. This actually happened to one of the kids. A block-aware board
   instead says: **"your 7:30 EB is inbound now, running WB, 4 late, three stops from the
   turnaround."** No consumer app does this.

The unifying idea: make complexity legible rather than hiding it. Density is the feature.

## Constraints

- Mobile-first. Used on phones, by a parent and by kids standing at stops.
- Must cover an arbitrary set of routes (a watchlist), not one hardcoded route.
- All-buses view must include deadheading / non-revenue vehicles (142 of 395 at time of writing).
- **The ladder must be switchable between one direction and both directions on a route.**
  Filtering to a single direction hides the inbound vehicle that is about to turn around and
  become the outbound one. This is not hypothetical; it stranded a rider looking at Transit.
- **Saved watches must be day-type aware** (weekday / Saturday / Sunday / exception day) and must
  not store a raw trip ID, because trip IDs change on exception days and at each schedule reset.
- **No new paid services.** Hosting must use what already exists: PHP-capable Linode servers the
  user already runs, and/or GitHub Pages. This rules out Cloudflare Workers, Fly, Vercel
  functions, and any managed platform that adds a bill or a new account to maintain.
- Must survive neglect. The predecessor site died; this should not die the same way.
- Personal side project. No users to answer to, no revenue, no deadline.

## Premises

1. **Dispatch board, not arrival predictor.** Success is "I understand the picture in three
   seconds," not "it gave me a number." Density is a feature.
2. **Route selection driven by live data, never hardcoded.** All-buses system view exists but
   is secondary, and includes deadheads.
3. **Schedule adherence is the differentiating feature** versus Transit, and it requires GTFS
   static, which requires a build/refresh step.
4. **A small always-on server is acceptable** where it is meaningfully more performant.
   (Relaxed from an original "no runtime backend" premise by the user, independently and in the
   same session that Codex named it the weakest premise.)
5. **Deliverable is a URL** opened on phones. Distribution is part of the design.

## Verified Data Facts

Every item below was probed live against the real endpoints on 2026-08-19, not assumed.

| Feed | Dataset ID | Observed |
|---|---|---|
| Vehicle Positions (JSON) | `cuc7-ywmd` | 200, 121 KB, 390-395 vehicles |
| Vehicle Positions (PB) | `eiei-9rpf` | 200, 33 KB |
| Trip Updates (JSON) | `mqtr-wwpy` | 200, 1.9 MB, 913 trip updates |
| Trip Updates (PB) | `rmk2-acnw` | 200, 401 KB |
| Service Alerts (JSON) | `9zu9-jwr2` | exists |
| GTFS static | `r4v4-vz24` | 11.3 MB zip / 66 MB unzipped |

- `.pb` is Protocol Buffers (GTFS-Realtime). **Decoding it is unnecessary**: JSON variants of
  both realtime feeds are current and live. The user's assumption that the JSON positions feed
  was retired is incorrect; `cuc7-ywmd` is serving fresh data.
- `data.texas.gov` returns `Access-Control-Allow-Origin: *`. Browsers can fetch directly.
- **Realtime-to-static trip join is exact: 256 of 256 live trip IDs matched GTFS `trip_id`.**
- Trip Updates carry `vehicle.id` as well as `trip.tripId`; 93% of active vehicle trips have a
  matching trip update.
- Trip Updates contain **predicted** stop times only, with **no `delay` field**. Computing
  lateness therefore requires GTFS `stop_times.txt` (841,087 rows, 71 routes, 24,295 trips).
- `trip.startTime` is present on every vehicle, so "this is the 5:14pm bus" needs no static data.
- Payload sizes measured for per-route sharding: route 5 schedule slice = 1.0 MB raw /
  **180 KB gzipped**; all 71 routes = 25.1 MB / 4.3 MB gzipped; stops lookup = 121 KB / 40 KB gzipped.
- GTFS static was republished 2026-08-18, one day before this session. Shards must be regenerated
  on a cadence or lateness numbers silently rot.
- The six routes in play are all live: 800 (15 buses), 4 (5), 837 (12), 337 (8), 350 (4), 7 (13).
- Saved-watch example resolves cleanly: "7:50a 800 SB from Simond/Berkman" is stop `6293`
  (Simond SB), trip `3010894_22201`, scheduled `07:52:09`, headsign "800 Goodnight SB".

### Blocks and the turnaround (verified)

- Route 4's 834 trips run on only **10 `block_id` values**, with **175 direction flips inside
  blocks**. A block is one physical vehicle's day.
- **Campbell/5th (stop `6243`) is confirmed as the turnaround**: it is the first stop of 407
  trips and the last stop of 407 trips.
- Worked example, one vehicle: block `4031`, trip `3014695_15713` (dir 0, WB) arrives
  Campbell/5th 07:25; trip `3014759_15051` (dir 1, EB) departs Campbell/5th 07:30. Five-minute
  layover, same bus, different trip ID, opposite direction.
- The Austin High special is also block-linked: block `1010`, trip `3014700_15476` (dir 0) ends
  at Veterans/Atlanta 08:42, and trip `3014765_15061` (dir 1) starts there at 08:59.
- Consequence: "where is my eastbound bus" is answerable well before the bus is eastbound, by
  following `block_id` backward to the currently-running inbound trip.

### Service calendar and trip ID stability (verified)

- The feed ships **no `calendar.txt`**; service is expressed entirely through
  `calendar_dates.txt` (589 rows, 29 service IDs, 145 distinct dates).
- `feed_info.txt`: valid **20260818 to 20270109**, version `260818_1456`. This matches the user's
  understanding that CapMetro fully resets the schedule roughly three times a year.
- Service `1-172` covers **95 dates, all Mon-Fri** (20260824 to 20270108). Within that span,
  weekday trip IDs are stable day to day. `6-172` covers 20 Saturdays.
- **However**, single-date service IDs exist: `2-172`, `3-172`, `4-172`, `5-172` cover exactly one
  date each (Aug 18, 19, 20, 21) and carry 2,388 trips apiece. These are first-week-of-school
  one-off schedules. 2026-08-19 falls on `3-172`.
- **Design rule:** a saved watch stores (route, direction, stop, scheduled time, day type) and
  resolves to the live trip ID via `calendar_dates.txt` at load time. Storing a trip ID would
  break on exception days and at every schedule reset.

### End-to-end verification performed

A throwaway script joined live positions + live trip updates + GTFS static and produced real
schedule adherence for route 4 at 9:35:23 AM CT:

```
#2216   9:33am trip   +1m   next 2730 7th/Pleasant Valley   pred 9:35 vs sched 9:34
#2858   9:17am trip   +0m   next 714 6th/West               pred 9:36 vs sched 9:35
#2641   9:33am trip   +3m   next 504 Campbell/5th           pred 9:36 vs sched 9:33
#2867   8:59am trip   -0m   next 2719 Cesar Chavez/PV       pred 9:35 vs sched 9:35
#2701   9:17am trip   -3m   next 1601 7th/Comal             pred 9:34 vs sched 9:38
```

This is the core technical claim of the design, exercised against production data rather than
asserted. A rendered sketch using this data is at `/tmp/gstack-sketch.png` (regenerable).

### Known data caveats

- Several trips share an identical scheduled time at a stop (07:42:09 / 07:42:17 / 07:42:40 on
  route 800 SB). These are different service calendars. Saved watches must resolve against
  `calendar_dates.txt` for the current service day, not by clock time alone.
- 7% of active vehicles have no matching trip update. Those need a graceful "position known,
  lateness unknown" state rather than a blank.
- Direction matters on the string-line board. A westbound ladder correctly shows no eastbound
  vehicles; the UI must make the active direction obvious to avoid reading as "no buses."

## Cross-Model Perspective

Codex ran a cold read with no access to the conversation, receiving only a written summary.

- **Coolest unconsidered version:** a "route operations strip" pairing the map with a
  string-line / Marey board: stops vertical, time horizontal, gray scheduled diagonals, live
  buses as colored dots riding them. Its argument: the three-second read is not "where is my
  bus" but "are buses evenly spaced, which is mine, is the route melting down," and a ladder
  answers that better than a map.
- **What it thought excites the user:** the phrase "dispatch board." Its read: "the fun part is
  not hiding complexity. It is making complexity legible."
- **Suggested 50% starting point:** OneBusAway. **Rejected in this design** as far too heavy;
  it is an agency-scale Java platform oriented around arrival prediction, which is explicitly
  not the goal. MapLibre plus a small build script is the real 50%.
- **Premise it called weakest:** the original no-backend premise, on phone battery and CPU
  grounds. The user relaxed that premise independently, before seeing this critique.
- **Its skip list, adopted:** no accounts, no notifications, no history, no home-grown arrival
  prediction, no attempt to fix or clone realtimebustracker.com.

Independent web research converged on the same display: string-line / time-distance diagrams are
long-established transit operations practice for exactly this problem.

## Prior Art

- **realtimebustracker.com** — the site being replaced. Its backend is *not* dead: the Cloud Run
  signed-URL service returns 200, the GCS object behind it holds 390 fresh vehicles, and CORS is
  open on both. The failure is client-side. Unconfirmed hypothesis: `map.js` fires
  `fetchSignedUrl()` and `fetchDataAndUpdate()` as parallel promises so the first fetch runs with
  an empty URL, and the page loads an **11.6 MB** `busroutes.geojson` on every load. Not verified
  in a browser; treat as a lead, not a diagnosis.
- **Instabus** (github.com/luqmaan/Instabus, 75 stars) — a no-backend CapMetro realtime map on
  GitHub Pages. Proves the browser-only approach worked for this exact agency. Unmaintained
  since 2018, so there is no live project being duplicated.
- **Mohiuddin, "Visualizing Bus Schedule Deviation"** — computed the same lateness metric but had
  to spatially join GPS pings to stops within 15 meters and hand-filter outliers over 1000 seconds.
  **That entire class of problem does not apply here**, because CapMetro publishes
  `currentStopSequence` and `stopId` on every vehicle. The join is exact on
  `(tripId, stopSequence)`. The conventional approach to this problem is unnecessarily hard for
  this feed.

## Approaches Considered

### Approach A: Browser-only static
Static site on Pages; build script pre-generates per-route schedule and pattern shards; browser
fetches `data.texas.gov` directly. Effort S-M, risk low. Nothing to keep alive. Rejected because
the phone downloads a 180 KB schedule shard and joins 390 vehicles against 913 trip updates every
refresh, on mobile data, at 7am.

### Approach B: Thin prejoin worker (SELECTED)
A small always-on worker polls the feeds every ~15s, joins positions + trip updates + GTFS
schedule + trip patterns, and serves one compact route-state JSON per route. The phone renders.
Effort M, risk low-medium.

### Approach C: Ladder first, map second
Approach A's architecture with the string-line board promoted to primary and the map demoted to a
tab. Rejected as the primary framing because the user explicitly asked for the map ("I like 1 -
the map so I have the most info"), though the ladder is retained as a co-equal panel.

## Recommended Approach

**Approach B, thin prejoin worker.**

Rationale:
- The user stated hosting is acceptable if it buys performance.
- Special-trip pattern diffing and schedule joins are work that should happen once centrally
  rather than on every device every 15 seconds.
- Codex independently flagged phone battery and CPU as the real risk.
- It keeps the door open for saved-watch evaluation and, later, history, without redesign.

Mitigation for the "it will die like the last one" risk, which is real and is the single biggest
threat to this project:

- **Reuse existing infrastructure.** Cron plus PHP on a Linode the user already maintains beats a
  new managed platform, because there is no new bill to lapse, no new account to lose access to,
  and no free tier to be discontinued. Note that the predecessor site died with a *working*
  backend on Cloud Run; novelty of platform was not what saved it.
- **No long-lived process.** Cron writes JSON files. If a run fails, the previous file is still
  served. There is nothing to crash or restart.
- **Degrade, do not die.** If the generated JSON is stale or missing, the client falls back to
  fetching `data.texas.gov` directly for positions only, showing buses with no lateness and a
  visible "schedule data unavailable" state. A dead backend downgrades the app rather than
  producing a blank map, which is precisely the failure the user experienced with the old site.

## Architecture Sketch

The "worker" is a **PHP script on the existing Linode**, run on a cadence, writing plain JSON
files into the webroot. There is no long-lived process and no new service. Apache/nginx serves the
generated JSON as static files, which is fast, cacheable, and cannot crash.

```
cron (Linode)                                       webroot (static JSON, served by existing httpd)
  build.php  every ~30-60s                     ──>  /api/route/{id}.json   compact route state
    fetch cuc7-ywmd  positions                      /api/all.json          all vehicles + deadheads
    fetch mqtr-wwpy  trip updates                   /api/watch/{id}.json   saved-trip status
    join on tripId + stopSequence
    + trip-pattern classify, + block chain
    + lateness math
  gtfs.php   daily
    fetch r4v4-vz24, rebuild schedule shards   ──>  /data/route-{id}.json  schedules + patterns
                                                    /data/stops.json
```

Client is a static bundle, deployable to GitHub Pages or the same Linode.

client (mobile web)
  route picker (live) │ direction toggle │ watchlist │ all-buses tab
  map panel  ......... MapLibre or Leaflet, vehicle chips w/ lateness badge
  ladder panel ....... string-line: stops vertical, time horizontal, NOW line
  vehicle rows ....... "#2641 · 9:33am trip · +3m · next Campbell/5th 9:36 (sched 9:33)"
```

Color language for adherence: blue early, green on time, amber 3-6 late, red 7+, hollow gray
deadhead, purple special pattern.

## Open Questions

1. ~~Where does the worker run?~~ **RESOLVED: existing Linode, PHP, cron-driven, writing static
   JSON.** No new paid services. Remaining sub-question: cron's floor is 60 seconds, while the
   feeds refresh every ~15-30s. Either accept up to 60s staleness (probably fine, since the
   underlying prediction does not change that fast), or run a small looping script under systemd
   that regenerates every 20s. Start with plain cron and only escalate if 60s feels stale in real
   morning use.
2. **Ladder legibility on a phone.** The rendered sketch is 1180px wide. A route with 20+ stops
   over a 60-minute window on a 390px screen is unproven. May need horizontal scroll, a stop
   subset, or a rotated layout. This is the biggest unvalidated design risk.
3. **How to draw both directions on one ladder.** Now a requirement, not an option. Options:
   mirror the two directions around a shared time axis, fold the route into an out-and-back
   loop so the turnaround sits at the fold, or overlay with distinct line styles. Unresolved,
   and it interacts badly with question 2 on a narrow screen.
4. **Transfer chains.** The kids' trips are 800→4 and 337→7→837. Does the board model a chain
   explicitly (does the connection hold?), or just show a watchlist of routes side by side?
   Chains are the more useful answer and the much harder build.
5. **Two kids, two schedules.** Whether this needs profiles, or just an unstructured list of
   saved watches that happen to belong to different people.
6. **How far do "special pattern" and block-turnaround generalize?** Both verified thoroughly on
   route 4 only. Must be checked on 800, 337, 350, 7, and 837 before either is promised as a
   headline feature. Route 4 having only 10 blocks may not be typical.
7. **Refresh cadence for GTFS static.** The feed is valid for ~5 months, but exception-day service
   IDs mean the *set of valid trips* changes daily even within one feed. Daily refresh is the
   safe default; the open question is how to detect a mid-period republish.

## Success Criteria

- Opening the app on a phone answers "is her bus late" in under three seconds without tapping.
- A saved watch for the 7:50a 800 SB at Simond/Berkman shows meaningful status from roughly an
  hour before until the bus clears the stop, and keeps working after the January schedule reset.
- When a route 4 bus is running the Austin High special pattern, the board says so, naming the
  stop it adds and the stop it skips.
- **Standing at Campbell/5th waiting for an eastbound 4, the board shows the inbound westbound
  bus that is about to become it.** This is the specific failure that stranded a rider on
  Transit, and fixing it is the sharpest test of whether this app is better.
- The all-buses view shows deadheads distinctly rather than hiding them.
- It still works, unattended, twelve months from now.

## Distribution Plan

- **Zero new recurring cost.** Everything runs on infrastructure already paid for.
- Static client on GitHub Pages, or served from the same Linode. Either works; Pages keeps the
  client alive even if the Linode is down, which pairs well with the degraded-mode fallback.
- `build.php` and `gtfs.php` run from cron on the existing Linode. Nothing to deploy, nothing to
  keep warm, no platform account to maintain.
- GTFS static refresh runs daily and regenerates route shards. A failed refresh must alarm
  visibly in the UI rather than silently serving stale schedules, because stale schedules produce
  confidently wrong lateness, which is worse than no lateness.
- CI: GitHub Actions for client build and Pages deploy on merge. The PHP side is a `git pull`.
- No app store, no accounts, no install. A URL, saved to a home screen.

## Next Steps

1. **Worker skeleton.** Poll `cuc7-ywmd` and `mqtr-wwpy`, cache in memory, serve
   `/api/route/{id}` with the join already done. The joining logic is already proven; port the
   throwaway script.
2. **GTFS ingest + shard build.** Download `r4v4-vz24`, emit per-route schedules, stop lookups,
   precomputed trip-pattern classifications (baseline vs special, with adds/skips), **block
   chains (trip → next trip in block)**, and a day-type → service-ID index from `calendar_dates`.
3. **Client shell.** Route picker from live data, direction toggle with a both-directions option,
   vehicle rows with lateness badges. This alone is already more useful for the stated purpose
   than the app being replaced.
4. **Block-aware inbound display.** For a chosen direction, also surface the inbound vehicle
   whose block continues into an upcoming outbound trip. Highest value per line of code in the
   whole plan, because it fixes a failure that actually happened.
5. **Map panel.** MapLibre or Leaflet, vehicle chips colored by adherence.
6. **String-line ladder.** Port the SVG renderer from the sketch. Solve the phone-width problem
   and the both-directions layout together, since they conflict.
7. **Saved watches.** (route, direction, stop, scheduled time, day type) resolved against
   `calendar_dates.txt` for the current service day. Start with the 7:50a 800 SB at Simond.
8. **All-buses view** including the ~142 deadheads.
9. **Deferred:** transfer chains, notifications, history, accounts, the second kid's profile.
